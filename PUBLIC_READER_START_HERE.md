## 1. What Collapse Aware AI Is

Collapse Aware AI (CAAI) is proprietary middleware for **retained-state behavioural selection**.

It is designed to sit between a host system and an underlying model, scripted logic layer, simulation runtime or decision engine.

Its purpose is not simply to store memory, retrieve context or generate text.

Its purpose is to determine **how relevant retained prior state may influence which permitted behaviour is selected**, while preserving a reference path and inspectable evidence.

In simple terms:

> CAAI is not the base model.  
> CAAI is the retained-state selection and evidence layer around an existing system.

## 4. Core engineering idea

Most AI memory systems focus on:

> What information should be stored or retrieved?

CAAI focuses on:

> **How should retained prior state influence which permitted behaviour wins, and how can that change remain inspectable?**

The public runtime shape is:

```text
Host / application
        ↓
Current event + permitted candidates
        ↓
Phase-2 retained-state / continuity sidecar
        ↓
CAAI integration boundary
        ↓
Sealed Crown/Core final selector
        ↓
Durable Decision Record
        ↓
Customer-safe evidence projection
        ↓
Managed evaluation comparison / export
```

The host remains the authority for world observation, candidate generation, domain truth and external action execution.

The current integrated package is suitable for:

- controlled technical demonstration;
- paid managed evaluation;
- bounded buyer-specific evaluation scenarios;
- pilot design;
- integration discussions;
- licensing discussions.

The current boundary is **local managed evaluation**, not public SaaS, unrestricted customer self-service or finished customer-hosted production deployment.

## 8. What can be evaluated now

A technical or commercial evaluation can ask:

1. Does retained state alter later candidate selection under controlled matched conditions?
2. Are reference and governed conditions distinguishable and inspectable?
3. Does state persist and remain available after restart?
4. Can seeded behaviour be replayed deterministically in the tested conditions?
5. Are revoked / wrong-scope / stale items blocked before influence?
6. Are durable Decision Records produced for committed selections?
7. Can customer-safe evidence be projected without exposing Crown internals?
8. Do failure, duplicate and ambiguous-delivery cases remain honest rather than silently retrying or fabricating success?
9. Can the full workflow be run as a bounded managed evaluation with customer-safe exports?

These are observable engineering questions.

## 9. Current Phase-2 components

The implemented Phase-2 line includes, in public-safe terms:

- **revisable retained state** — important events can be reinforced, weakened, reframed, resolved, revoked or retired;
- **continuity state** — strong anchors, compact continuity memory and session boot;
- **memory-use evidence** — distinction between state being loaded and state being explicitly reported as consumed/considered/ignored;
- **ambiguity handling** — bounded competing interpretations, clarification and confidence posture;
- **recall quality** — routing, judging, corrective recall and revoked-context protection;
- **agency-impact routing** — bounded direct completion, scaffolding, clarification, preview, defer/block routes;
- **Evaluation Forge** — versioned metrics, comparisons, observability and evidence bundles;
- **live integration layer** — formal contract, adapter, Core-boundary mapping, live selector linkage and evidence projection;
- **hardening** — restart, replay, duplicate protection, failure transparency and reconciliation;
- **managed-evaluation packaging** — guided local workflow and buyer-safe exports.

Broader optional ideas such as affective signals, robotics inputs, behavioural-consistency research and outcome-driven reinforcement remain separate future / Phase-2+ work unless explicitly implemented and evidenced later.
