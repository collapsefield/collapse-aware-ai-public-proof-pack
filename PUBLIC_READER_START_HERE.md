## 1. What Collapse Aware AI is

Collapse Aware AI (CAAI) is proprietary middleware for **governed retained-state behavioural selection**.

It is not simply a memory store, retrieval layer or chatbot wrapper.

Its core question is:

> **When should retained history be allowed to change current behaviour — and when should the system deliberately ignore it?**

A host supplies the current situation and the behaviours/actions that are genuinely permitted. CAAI governs whether retained history should influence which one wins.

> **Retained history is eligible evidence, not automatic authority.**

## 2. Current engineering state

The current programme has two distinct layers.

### Core Gold Build

The **Core Gold Build** is the frozen commercial selector foundation.

Public-safe accepted capabilities in the integrated lineage include:

- host-supplied permitted candidate selection;
- reference and governed retained-state conditions;
- persistence / restart recall;
- deterministic replay in tested conditions;
- retained-state revision and revocation;
- validation and bounded fallback behaviour;
- durable Decision Records and customer-safe evidence;
- managed evaluation and evidence export.

Core Gold is the finished selector foundation currently available for commercial evaluation, pilot, integration and licensing discussions.

### Evolution 2

**Evolution 2** is the richer continuity engineering branch built around the same governed-selection principle.

Current private engineering checkpoints include:

- structured ContinuityFrame interpretation;
- bounded hybrid retained-state retrieval;
- Open Loops / Reopen Semantics;
- Interaction Fit;
- suppression and bounded proactive controls;
- Confidence / Clarification;
- Contradiction / Change Surfacing;
- record-only Outcomes;
- Agent Self-History;
- bounded turn-local behavioural signals;
- Session Observation foundation;
- Engineering Tuning;
- a restart-safe local Engineer Model with microphone speech-to-text input.

A clean current-task/reference behaviour remains a genuine competitor to history-conditioned alternatives, and final selection authority remains separated from candidate generation.

Evolution 2 remains an **Engineering build rather than a finished Production release**.

## 3. Why this is different from ordinary AI memory

Many memory systems ask:

> What should be stored or retrieved?

CAAI asks:

> **How should retained prior state influence final selection among permitted behaviours while preserving a clean reference path and inspectable evidence?**

The difference matters because remembering more is not always better. Old, wrong-scope, stale or socially inappropriate history may need to stay silent even when it is retrievable.

## 5. Game / NPC and simulation relevance

Games are a natural fit because the host already owns structured world truth:

- player / NPC identities;
- quests and unresolved matters;
- witnessed events;
- locations and world state;
- permitted actions;
- save / restart identity.

The game keeps those authorities. CAAI can govern whether retained player/NPC history should influence which permitted behaviour wins.

CAAI is host-neutral and suitable for buyer-specific adapter work. It is not currently represented as a finished Unity, Unreal or Godot production SDK.

## 6. What can be evaluated now

A bounded technical or commercial evaluation can ask:

1. Does retained history alter later selection under controlled matched conditions?
2. Does the clean current-task/reference condition remain available?
3. Does retained state persist across restart?
4. Can tested behaviour be replayed deterministically where the accepted path supports it?
5. Are stale / revoked / wrong-scope items prevented from silently acting as current authority?
6. Are committed decisions recorded and projected into customer-safe evidence?
7. Can richer continuity features such as unresolved-state handling, clarification or change surfacing improve a bounded longitudinal scenario?
8. Can the system remain inspectable without exposing proprietary Crown/Core internals?

These are observable engineering questions.
